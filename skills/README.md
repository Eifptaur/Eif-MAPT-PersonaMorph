# Skill：怎么写、怎么加进来

> 本目录（`skills/`）就是"教机器人**什么情况该按什么套路做**"的地方。
> 一个 skill 就是一个 Markdown 文件，放进来、开总开关，模型就能自己判断该不该用。

---

## 一、先说清楚它和"工具"有什么不一样（别放错）

| | **Skill**（就是这里） | **工具**（`tools.d/`） |
|---|---|---|
| 是什么 | **一段给模型看的说明书**（Markdown 正文） | 一个**能被调用的函数**（打 HTTP 接口） |
| 有没有代码 | **没有**（纯文本，不执行任何东西） | 有（会真的发请求） |
| 谁决定用不用 | **模型自己判断**（先看清单，觉得用得上才去读正文） | 模型按 schema 决定调不调，**调了就执行** |
| 适合什么 | "遇到这种情况，按这个套路说/做" | "去查一下这个数据""打这个接口" |

一句话判据：**规则能写死的走工具，要理解人话的走 Skill。**

> 例：写"查天气要用哪个接口" ⇒ 放 `tools.d/`；
> 写"群友失恋时该怎么回话" ⇒ 放这里。

---

## 二、怎么写（两种形态，功能完全一样，挑顺手的）

**形态 A：单个文件**（简单，推荐先从这个开始）

```
skills/
  comfort-heartbreak.md
```

**形态 B：目录包**（正文长、或想带参考附件时用）

```
skills/
  comfort-heartbreak/
    SKILL.md          ← 必须叫这个名字（大写 SKILL.md）
    (可选) 参考话术.md
```

> ⭐ **文件（或目录）名就是它的 id** —— 必须是小写字母/数字加 `-`（见第四节命名规则）。
> 两型**功能完全一样**，只是"想不想带附件"的区别。

---

## 三、正文怎么写

### 头部（推荐加，但**没有也能用**）

```markdown
---
name: 安慰失恋的人
description: 群友失恋、被甩、感情受挫时，怎么回话才不招人烦
---

# 具体怎么做

（下面就是正文，写你希望它照着做的内容）
```

- **`description` 很关键**：模型**只看这一句**决定要不要读正文。写清"**什么时候用**"，
  别写成"本 skill 用于……"这种废话。
  好例子：`群友失恋、被甩、感情受挫时，怎么回话才不招人烦`
  坏例子：`情感支持 skill`
- ⛔ **没有 `description` 会被拒收**（模型没有依据判断该不该读，等于装了永远不触发），
  面板里会明确告诉你缺什么 —— 不会静默当成"能用"。
- `name:` 是**给人看的显示名**（可以写中文），**不参与识别**：
  识别与落点一律用**文件名/目录名**那个 id。写不写都行，写了更好看。

### 正文的建议结构

1. **什么情况该用**（触发条件，写具体）
2. **该怎么做**（分步骤，越具体越好）
3. **不要做什么**（反面清单往往比正面清单更有用）
4. **例子**（两三段真实对白，比一段描述管用得多）

---

## 四、命名规则

- **小写字母开头**，中间可以用 `-` 和数字：`comfort-heartbreak`、`reply-3am`
- 不许大写、空格、下划线、中文、斜杠
- 最长 40 个字符
- 同名两份 ⇒ **两个都不收**（面板会说清楚，先改名再放）

---

## 五、默认状态

- 总开关（`skills.enabled`）**默认关**：关着时清单不注入、`skill` 工具也不注册 —— **一处关掉全失效**。
- 开关在控制台的「工具与插件」那一带（配置键 `skills.enabled`）。
- ⛔ Skill **只能提供正文**：不能注册工具、不能改发送逻辑、不能改落点。
  想加能执行的东西，请走 `tools.d/`（声明式 HTTP，也不跑本地代码）。
